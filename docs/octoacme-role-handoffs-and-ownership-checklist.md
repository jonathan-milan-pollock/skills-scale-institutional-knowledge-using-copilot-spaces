# OctoAcme — Role Handoffs & Ownership Checklist

## Purpose
Standardize who leads, contributes to, and signs off on key project activities so teams can reduce ambiguity during handoffs.

## How to use
- Copy the table into a project README, one-pager, or release doc at project kickoff.
- Replace role names with named individuals for the current project.
- Mark optional roles only when they are needed for the project.
- Add links to the evidence or artifacts used to confirm each handoff is complete.

## Lifecycle Ownership Template

| Lifecycle Stage | Key Activity | Primary Owner | Core Collaborators | Suggested Evidence / Artifact | Handoff / Decision Gate |
|---|---|---|---|---|---|
| Initiation | Problem statement, goals, and success metrics defined | Product Manager | Project Manager, Stakeholders, Data Analyst / Analytics Lead | Project one-pager | Approve move into planning |
| Initiation | Stakeholders, team roles, and timeline identified | Project Manager | Product Manager, Engineering Manager, Stakeholders | Stakeholder list, initial timeline, proposed team roles | Confirm owner for each planning artifact |
| Planning | Backlog, milestones, and acceptance criteria prepared | Product Manager | Project Manager, Developers, UX/UI Designer, QA/Testing | Prioritized backlog, milestone plan, acceptance criteria | Planning complete and ready for execution |
| Planning | Delivery capacity, dependencies, and technical approach confirmed | Engineering Manager | Developers, Project Manager, DevOps / Platform Engineer, Security / Compliance Lead | Capacity plan, dependency list, technical notes | Team can commit to execution scope |
| Execution | Work tracked, blockers escalated, and risks updated | Project Manager | Developers, Product Manager, Engineering Manager | Project board, status update, risk register | Major blockers triaged within agreed escalation path |
| Execution | Feature implementation, quality checks, and design validation completed | Developers | QA/Testing, UX/UI Designer, DevOps / Platform Engineer | Pull requests, test evidence, design QA notes | Work meets definition of done |
| Risks & Communication | Material risks, approvals, and stakeholder updates managed | Project Manager | Product Manager, Security / Compliance Lead, Stakeholders | Risk register, decision log, weekly status update | Open risks have owners and mitigation plans |
| Release | Release readiness, deployment steps, and rollback plan confirmed | Release Manager or Project Manager | Developers, QA/Testing, DevOps / Platform Engineer, Customer Success / Support Representative | Release checklist, rollback plan, release notes draft | Go / no-go decision recorded |
| Release | Customer and internal communications prepared | Customer Success / Support Representative | Product Manager, Technical Writer / Documentation Owner, Stakeholders | FAQ, support notes, announcement draft | Support and stakeholder readiness confirmed |
| Retrospective | Outcomes reviewed and improvements assigned | Project Manager | Product Manager, Engineering Manager, Developers, Stakeholders | Retro notes, action item list, metrics review | Action items added to backlog with owners |

## Reusable Ownership Checklist
- [ ] A named individual is assigned for each primary owner role.
- [ ] Each lifecycle stage has a clear decision gate or completion signal.
- [ ] Required collaborators are identified before work begins.
- [ ] Evidence links are stored in the project repo or project board.
- [ ] Security, platform, analytics, support, and documentation roles are included when the work requires them.
- [ ] Release communications and support readiness have explicit owners.
- [ ] Retrospective action items have owners and due dates.
